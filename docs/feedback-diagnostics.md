# 问题广场、反馈对话与诊断日志

客户端的“问题反馈”是独立页面。用户填写问题并提交时，主进程固定一份当时仍保留的脱敏诊断日志快照，再通过现有授权后端上传。管理员在现有网页后台查看问题、处理状态和完整日志，可直接回复用户。用户在“我的反馈”中查看管理员答复并继续回复；问题和双方对话原文均存放在现有 GitHub 私有业务仓库。

网页「问题广场」公开展示所有已完成提交的问题、处理状态和公开评论。问题标题、说明及评论采用单独的脱敏投影；邮箱、令牌、常见联系方式和个人目录等可识别内容会被遮盖。原文仍保存在私有业务仓库，管理员与提交者的对话、诊断日志、账号字段及内部处理记录不进入公开接口。上传尚未完成的问题不会出现在广场。没有创建公开 GitHub Issues。

这里的“完整日志”指**本机当前保留范围内的全部诊断记录**，并非安装以来无限保存的所有记录。日志只从支持此功能的版本开始产生；轮转掉的记录、旧版本没有记录的行为、进程异常终止前未落盘的事件不能恢复。诊断日志不公开。

## 网页问题广场

- 未登录也可以查看问题列表和详情，按「全部 / 未解决 / 已解决 / 已关闭」、分类与关键词筛选；未解决包含待处理和处理中。搜索仅匹配脱敏后可见的标题与说明，不能以私密字段搜索。列表和评论各自分页，每页默认 20 条，最多 50 条。
- 使用现有软件账号邮箱和验证码登录即可评论，无需会员，不占用桌面设备名额。首次验证邮箱可创建账号。网页会话通过独立 `__Host-xhs-browser` Cookie 保存，具有 Secure、HttpOnly、SameSite=Strict 属性；网页退出不会退出管理后台。
- 每条公开评论最多 2000 字符，保留原文、换行和时间。评论平铺展示，不接受父评论、回复目标或自定义作者/角色。公开作者仅区分管理员和用户，不返回邮箱或用户 ID。
- 提交者登录后，在问题详情的私密对话区域查看完整回复并继续交流；其他用户不会获得该区域的数据。管理员仍在现有后台回复。公开评论不会写入私密对话，私密回复也不会成为公开评论。
- 发送失败保留草稿及请求编号；同账号、同编号与同原文重试只写入一次。服务端确认发送后，即使后续刷新失败，也先显示已保存消息。退出或切换账号会清空页面上的私密内容；草稿只在当前页面内存中按账号隔离，同账号重新登录可恢复，不会带到另一账号。公开评论还会在事务中核对草稿所属账号，防止其他标签页切换登录造成错账号发送。

公开接口：`feedback-public-list`、`feedback-public-detail`、`feedback-public-comment`。提交者的网页私密接口为 `feedback-owner-detail`、`feedback-owner-reply`，仅接受 browser 会话并验证问题归属。网页登录与退出复用 `send-code`、`verify-code`、`me`、`logout`，输入带 `client: "browser"`，登录响应不向 JavaScript 返回令牌。Cookie 请求必须符合配置的准确站点 Origin。

公开评论每账号每小时最多 20 条、每天 100 条，全局每小时 100 条、每天 300 条；幂等重试不会重复占用次数。每次评论事务在最新状态上重新校验身份、归属状态、限流和容量。评论不得使权威状态超过 700,000 字节，为原有 900,000 字节账号状态上限预留空间；容量不足时明确失败，不删除或截断任何历史文本。

## 用户操作

1. 打开桌面客户端的“问题反馈”页，查看日志文件数量、大小、保留时间范围和应用环境。
2. 选择问题类型，填写标题和详细说明。说明应包含操作步骤、预期结果、实际结果及出现的提示；不要粘贴 Cookie、验证码、激活码、密码或其他秘密。
3. 登录**软件账号**，点击“提交反馈与日志”。无需会员，设备被阻止或授权被撤销也可以反馈；小红书网页登录不能替代软件账号登录。
4. 等待日志上传和服务器完整校验。只有服务器确认最终提交后，界面才显示成功和反馈编号。
5. 网络失败后，保持同一软件账号、问题类型、标题及说明，再次提交可续传原快照。重启客户端或正常升级后也使用原请求编号和原版本信息重试，避免重复创建反馈。
6. 在“我的反馈”中打开已提交的问题，查看完整对话并补充回复。刷新后显示最新答复；无需重新提交诊断日志。每条回复最多 8000 字符，不允许纯空白内容。

未登录时可以使用“复制诊断信息”或“导出日志文件”，这两项只操作本机，不向后端上传。导出通过系统保存对话框选择位置。当前本机导出内容是 NDJSON，即每行一个 JSON 记录；即使选择 `.txt` 扩展名，内容仍是同一份 NDJSON。

修改问题类型、标题或说明视为不同的问题，会准备新的快照。已成功提交后再次提交相同文字，也会创建新的反馈并受发送频率限制。反馈中不包含提交快照之后发生的新事件；需要补充后续日志时应提交新的问题说明。

新问题的标题、说明和双方回复按输入原文保存，包括换行、空格、邮箱、路径和文字中的链接，不经过诊断脱敏或截断。诊断日志仍维持原有脱敏规则。旧版本已经脱敏保存的问题说明无法还原；旧反馈可以继续追加完整原文回复。

## 本机日志保留与隐私

默认存放在 Electron 的应用用户数据目录中，与程序安装目录分离：

- `diagnostics/events.ndjson`：当前日志。
- `diagnostics/events.1.ndjson` 至 `events.7.ndjson`：轮转历史，合计最多 8 个日志文件。
- `diagnostics/retention.json`：日志开始时间及已轮转字节数。
- `feedback-pending/<内容摘要>.json`：尚未确认提交成功的反馈快照与重试信息；成功后删除对应文件。

当前日志保留总量以 **8 MiB（8,388,608 字节）**为上限，快照还为诊断摘要预留空间。轮转先淘汰最早的文件；快照必要时继续丢弃最早的完整行，使最终上传内容不超过上限。待重试反馈缓存是独立的固定快照，会额外占用磁盘空间；不能把多个待提交快照的总大小理解为也只有 8 MiB。

主进程串行写入和截取日志；快照包含截取前已经排入队列的记录，之后的新记录不进入该快照。队列过载、损坏的日志行、轮转和裁剪都会在摘要中留下计数或标记。无法写入或读取日志时会记录错误状态，不能据此声称存在完整历史。

本机日志文件按 `0600`、目录按 `0700` 创建；Windows 最终访问权限仍由用户目录的系统 ACL 决定。日志不是加密保险箱，文件权限也不能代替脱敏。现有登录凭据继续由系统安全存储保护，不写入诊断目录。

记录范围以应用诊断所需的信息为限：启动、版本、操作系统及架构、页面切换、请求状态和耗时、任务数量、笔记序号、重试和错误类型、媒体音视频轨道检测结果、更新状态及异常等。日志可包含用于定位问题的笔记 ID 和不带查询参数的 URL 路径。

禁止把以下内容作为日志源：小红书 Cookie、账号会话令牌、请求认证头、验证码与激活码、GitHub/邮件密钥、原始硬件标识、网页原始 HTML、下载的媒体内容、任意请求或响应正文。调用方仅传递已选择的诊断字段；公共脱敏函数作为第二道保护处理秘密字段名、Bearer/JWT/PAT 等令牌形式、URL 用户信息及查询参数、邮箱、UUID 和个人目录路径。

本地落盘、导出与快照统一使用 `lib/diagnostic-sanitize.js`。服务器再次检查同一规则，发现未脱敏内容时拒绝整个分片，不会悄悄改写已锁定的哈希。自由文本识别无法证明任意字符串都不是秘密，因此不得新增整段 Cookie、完整请求体、原始页面等日志调用。

## 日志格式

每行必须是一个完整 UTF-8 JSON 对象，并以换行结束：

```json
{"at":"2026-09-21T08:00:00.000Z","level":"warn","event":"request.retry","details":{"attempt":2,"code":"NETWORK_TIMEOUT"}}
```

允许字段：

| 字段 | 含义 |
| --- | --- |
| `at` | ISO 时间，来自本机事件记录时间；不用于会员授权判断 |
| `level` | `debug`、`info`、`warn`、`error` |
| `event` | 事件名称 |
| `details` | 可选的脱敏 JSON 诊断字段 |
| `message` | 可选的脱敏说明文字 |

快照第一行是 `diagnostics.snapshot`，包含应用环境、日志容量、历史开始时间、轮转字节数、丢弃事件数、损坏行数、日志错误等。它的时间表示快照生成时间。清单中的日志范围使用其余保留记录时间戳的最小值和最大值，避免系统时钟回拨影响范围；没有其他记录时使用摘要时间。

服务器限制每行最多 32 KiB、每片最多 256 KiB。客户端正常事件采用更小的单行预算，超长事件缩减为诊断摘要。每个分片都由完整行组成，不能在 UTF-8 字符或 JSON 行中间切断。

## GitHub 数据结构

所有持久化后端业务数据继续存放在**同一个独立 GitHub 私有业务仓库**。没有新增数据库、KV、对象存储或公开 GitHub Issues。

权威状态文件仍使用 `AUTH_GITHUB_PATH`，默认 `state/accounts.json`。保持 `schemaVersion: 1`，新增字段采用兼容读取：旧状态缺少下列字段时按空对象处理，不清空已有用户、会话、会员或设备。

| 权威状态字段 | 用途 |
| --- | --- |
| `feedback` | 反馈元数据、私密对话 `messages`、独立公开评论 `comments`、固定日志清单、幂等摘要与提交状态，按反馈 UUID 索引 |
| `feedbackRateLimits` | 每账号及全局的提交时间记录，限制必须跨实例生效 |
| `feedbackReplyRateLimits` | 用户及管理员的回复时间记录，限制跨实例生效；只清理过期的限流时间，不删除对话 |
| `feedbackCommentRateLimits` | 公开评论的每账号及全局限流时间，原文和幂等摘要保存在对应反馈的 `comments` 中 |
| `operations` | 复用管理员操作幂等记录 |
| `audit` | 复用管理员日志，记录处理状态变更前后、管理员、时间与原因 |

反馈记录的主要结构如下，示例值不是生产数据：

```json
{
  "id": "12345678-1234-1234-1234-123456789012",
  "userId": "用户编号",
  "title": "问题标题",
  "description": "完整原始问题说明，保留换行和空格",
  "originalTextVersion": 1,
  "messages": [],
  "category": "audio",
  "appVersion": "客户端版本",
  "platform": "darwin",
  "arch": "arm64",
  "status": "uploading",
  "createdAt": "2026-09-21T08:00:00.000Z",
  "updatedAt": "2026-09-21T08:00:00.000Z",
  "submittedAt": null,
  "requestKey": "服务端HMAC摘要",
  "inputHash": "服务端HMAC摘要",
  "log": {
    "partCount": 2,
    "totalBytes": 123456,
    "sha256": "完整日志的64位十六进制SHA-256",
    "firstTimestamp": "2026-09-21T07:00:00.000Z",
    "lastTimestamp": "2026-09-21T08:00:00.000Z",
    "truncated": false,
    "parts": [
      { "bytes": 100000, "sha256": "第0片的SHA-256" },
      { "bytes": 23456, "sha256": "第1片的SHA-256" }
    ]
  }
}
```

`category` 为 `download/audio/update/account/other`；`platform` 为 `darwin/win32`；`arch` 可为 `arm64/x64/ia32` 或空值。标题最多 120 字符、说明最多 8000 字符；界面提供更明确的最少字数指引。

每条回复追加到同一反馈的 `messages` 数组，按 GitHub 状态事务提交顺序排列，包含 `id`、`authorRole`（`user/admin`）、`authorId`、`content` 和 `createdAt`，以及只在服务端保存的 `requestKey`、`inputHash` 幂等摘要。`content` 保存完整原文；没有编辑、删除、历史裁剪或自动归档操作。详情接口返回全部消息的公开字段，不能返回幂等摘要。旧反馈缺少 `messages` 时读取为空数组；兼容读取本身不写 GitHub。

`originalTextVersion: 1` 标记采用原文校验的新记录。旧版尚未上传完成的反馈继续接受原快照按旧脱敏规则计算的幂等摘要，从而可以续传；不会改写旧记录的正文。新记录相同请求编号的重试必须匹配完整原文，不能通过脱敏后的相同文本绕过冲突检测。

日志正文不嵌入权威状态，按如下路径写入独立的不可变文件：

```text
feedback/<反馈 UUID>/part-000.ndjson
feedback/<反馈 UUID>/part-001.ndjson
...
```

每份快照总量最多 8 MiB，最多 64 片，每片最多 256 KiB。允许 64 片是为了容纳整行分块的余量，并不将总量扩大到 16 MiB。GitHub Contents 返回的文件 SHA 用于文件及状态并发控制；清单中的 SHA-256 用于校验实际 UTF-8 日志字节，两者不可混用。

现有权威状态文件 **900,000 字节**安全容量限制仍生效。反馈说明、全部对话、清单和审计也占用该容量。达到上限时操作明确失败，不会假报成功，也不会自动删除历史记录。当前没有自动清理服务端反馈及 Git 历史的功能；如需长期扩容或归档，应在维持私有仓库为唯一存储的前提下另行设计迁移。

## 上传协议与一致性

所有调用均为现有 `POST /api/account`，JSON 使用 `{ "action": "...", "input": { ... }, "proof": { ... } }`。桌面调用附带既有 Bearer 会话令牌及 Ed25519 设备请求证明；这里的签名用于校验身份来源，不代表该设备获得会员功能授权。

| 操作 | 输入与结果 |
| --- | --- |
| `feedback-begin` | `requestId/title/description/category/appVersion/platform/arch/log`；固定完整清单并返回反馈编号与上传参数 |
| `feedback-upload-part` | `feedbackId/index/content/sha256`；仅允许反馈所属用户上传，分片必须匹配原清单 |
| `feedback-finalize` | `feedbackId/requestId`；读取并验证全部分片，最终 CAS 提交后才返回已提交状态 |
| `feedback-mine` | 返回当前账号自己的反馈摘要 |
| `feedback-detail` | `feedbackId`；返回自己提交的完整问题 `feedback` 和全部回复 `messages` |
| `feedback-reply` | `feedbackId/content/requestId`；向自己的已提交问题追加原文，返回 `feedback/message/replayed` |

流程：

1. 客户端把快照、完整及分片哈希、原应用版本和请求编号保存到待提交缓存。
2. `begin` 在 GitHub 文件 SHA 条件事务中校验会话、频率和幂等键，创建 `uploading` 记录。相同编号和内容重试返回原记录；同一编号改内容会拒绝。
3. 客户端以至少两秒间隔串行上传。服务器对每片验证身份、所属用户、字节数、哈希、行格式和隐私，然后创建文件。已存在且内容相同则返回重试结果；内容不同绝不覆盖。
4. `finalize` 读取全部分片，并校验逐片及整体字节数、SHA-256 和时间范围。随后重新读取权威状态、重新校验会话，在一次 SHA 条件事务中把 `uploading` 改为 `new` 并写入 `submittedAt`。
5. 最终响应丢失时重试返回已经存在的提交结果，不创建第二条反馈。客户端只有收到确认后才删除待提交缓存。

状态文件冲突会重新读取、重新验证并有限重试。日志文件写入和最终提交响应不确定时会明确报错；即使部分或全部日志文件已经存在，也不能把尚未最终提交的反馈显示为成功。上传完成前管理员可以看到“日志未上传完成”，但不能下载日志或修改处理状态。

默认频率为每账号每天最多 3 条新反馈、全局每小时最多 20 条新反馈，且两条新反馈的全局开始时间至少相隔 60 秒。限制记录在权威状态中。相同请求的续传不额外占用新反馈额度。客户端串行间隔和分片最早接收时间限制用于降低 GitHub 写入频率；GitHub 自身限流仍可能发生。

回复同样通过权威状态文件的 SHA 条件事务提交，冲突后重新验证身份、反馈归属、提交状态与限流。普通用户每小时最多 20 条、每天最多 100 条；管理员每小时最多 100 条、每天最多 500 条。相同作者和请求编号只追加一次，重试返回原消息，不重复占用额度；原文或目标反馈改变时拒绝复用请求编号。限流不会限制已经提交消息的原请求重试。

回复成功不改变处理状态；已解决或已关闭的问题也允许双方继续交流。未完成日志上传的问题不能回复。列表按最近更新时间排序，返回 `replyCount`、`lastMessageAt` 和 `lastMessageRole`；尚无回复时使用初始问题的提交或创建时间和 `user` 角色。对话读取、发送以及已成功请求的重试均重新检查会话；其他用户不能读取或回复不属于自己的问题。

## 管理员操作

1. 使用现有管理员邮箱登录 `/admin`。页面地址不是权限依据；所有反馈管理接口仍在服务器校验管理员角色和管理会话。
2. 打开“问题反馈”，按邮箱、用户 ID、标题、反馈编号或处理状态筛选。
3. 选择反馈查看问题说明、应用版本及架构、创建和提交时间、日志范围、大小及是否轮转。
4. 点击“查看完整日志”，后台通过管理员接口逐片读取；浏览器再次核对每片及完整 SHA-256，然后显示全部保留日志。
5. “复制反馈与完整日志”同时复制问题信息、账号、状态、环境、日志范围和完整 NDJSON。剪贴板被浏览器拒绝时显示可手动复制的完整文本。
6. “下载日志 NDJSON”保存原日志；“下载日志 TXT”转换为便于阅读的时间、级别、事件和详细字段文本，保留每一条记录。
7. 将反馈标记为“待处理 / 处理中 / 已解决 / 已关闭”，填写处理说明并确认。服务端记录操作者、时间、原因及变更前后状态；网络重试不重复记账。
8. 在对话区域直接输入回复并发送。发送确认前保留同一原文和请求编号；写入结果不确定时可重试，避免重复消息。状态处理说明属于内部审计记录，给用户的答复应通过对话回复发送。

管理员操作对应 `admin-feedback`、`admin-feedback-detail`、`admin-feedback-reply`、`admin-feedback-part`、`admin-feedback-status`。详情返回 `feedback/history/messages`；回复输入与普通用户相同，返回 `feedback/message/replayed`。管理页使用既有 `HttpOnly; Secure; SameSite=Strict` Cookie，POST 必须匹配配置的准确 HTTPS Origin，不能用普通桌面会话调用管理员接口。日志不会通过静态资源 URL 暴露。退出管理账号会清除页面保留的反馈内容和日志。

## 部署与最小权限

沿用现有 Vercel `/api/account`，没有新服务和新 Secrets。继续使用现有的 GitHub 私有业务仓库配置、`AUTH_SECRET_PEPPER`、管理员邮箱名单及准确的站点 Origin。邮件配置只用于原有账号登录，不因反馈而新增邮件发送。

GitHub 凭据仅授予**指定私有业务仓库**的 Contents 读写权限及仓库 Metadata 读取权限即可；无需代码仓库、Actions、Issues、Pull requests、组织管理或仓库管理权限。私有仓库必须已有配置分支。客户端仍只访问授权后端，不能获取 GitHub 凭据或直接访问日志仓库。

账户函数静态导入 `server/auth/feedback.js`，并通过该模块导入共享脱敏函数。Vercel 文件追踪必须包含 `server/auth/**`、`lib/diagnostic-sanitize.js` 和现有运行依赖。静态输出只发布允许的网页及管理页文件，不发布 `server`、`state`、`feedback`、本机诊断目录或 `.env`。桌面包包含本机日志及共享脱敏模块，不包含 `api/account.js` 或服务端私钥。

`feedback-begin`、`feedback-reply` 和 `admin-feedback-reply` HTTP 请求上限为 48 KiB，足以承载 8000 字符的中文回复及 JSON 转义；分片上传 HTTP 请求上限为 1,600,000 字节以容纳 JSON 转义开销，实际 UTF-8 日志内容仍严格限制为 256 KiB。其他接口保留原有 16 KiB 请求上限。Vercel 账户函数最大执行时间为 60 秒，完整校验请求使用相应的客户端超时。

## 故障和恢复

| 情况 | 实际处理 |
| --- | --- |
| 未登录、会话已撤销 | 不上传；重新登录同一账号后可重试原反馈 |
| 账号或会员受限、设备已撤销授权 | 保留身份校验，允许反馈；不恢复会员或下载权限 |
| GitHub 超时、429、403 或写入响应丢失 | 返回失败/结果未确认；保留本机快照及请求编号，稍后重试 |
| 仅部分日志已保存 | 仍为 `uploading`，管理员不可下载，最终提交不会成功 |
| 分片或整体哈希不符 | 拒绝完成；不会替换已保存日志或悄悄改写清单 |
| 日志包含未脱敏内容 | 拒绝该分片；修复或更新客户端脱敏逻辑后重新收集，不能关闭服务端检查绕过 |
| 本机缓存损坏 | 明确提示无法校验；可导出当前日志并联系管理员，不使用损坏快照继续上传 |
| 频率达到上限 | 等待提示期限；相同已有反馈可以继续上传 |
| 服务端状态达到容量上限 | 明确拒绝写入，需管理员安排容量或迁移；不删除历史、不假报成功 |
| 应用退出或升级中断 | 保留未确认的反馈缓存；下次同账号、同问题内容重试使用原快照 |

没有自动把未知状态当作成功，也不会因反馈失败而修改会员、解绑设备或删除原下载任务及文件。
